# DHIS2 backup and restore

Operate the backup tooling installed by the `backups` role (triggered for `[databases]` hosts).

## Safety rules

1. **Restore is destructive** — it replaces the target database. Before restoring: name the exact target database, confirm with the human in writing, and take a fresh backup of the current state first.
2. Never disable or skip the audit-table handling silently: the backup script **dumps and then truncates** the `audit` table as part of its cycle. Restores must account for archived audit dumps.
3. S3 credentials are secrets — `s3_access_key`, `s3_secret_key`, `s3_cluster_id`, `s3_bucket` belong in `host_vars/postgres/vault.yml` (encrypted). See the dhis2-vault skill.
4. A backup that has never been test-restored is not a backup. Recommend a periodic restore test into a scratch database.

## Credential access

**Default deny:** do not read, decrypt, or print secrets unless a step in this skill explicitly requires it. Backups dump via `lxc exec postgres -- pg_dump` (LXD) or local `pg_dump` as the postgres OS user (SSH) — no DHIS2 DB password needed. Always use `sudo`: the script is typically mode `0700` root:root and `dhis2-env` is `0600` root:root, so unprivileged `test -x` / `cat` falsely reports "missing". Grep non-secret flags from `dhis2-env` only; never print S3 keys, passphrase files, or vault contents.

## Where the script actually lives

The role targets `[databases]`, but **installation location depends on `ansible_connection`**:

| Mode | Script and dumps live on | How dumps run |
| --- | --- | --- |
| LXD (`ansible_connection=lxd`) | The **LXD hypervisor host** (not inside the postgres container). `backups/tasks/lxd.yml` switches to `ansible_connection=local`. | `lxc exec postgres -- pg_dump ...` from the host |
| SSH (`ansible_connection=ssh`) | The database server itself | Direct `pg_dump` on that host |

Do **not** `lxc exec postgres` to find or run `dhis2-backup` in LXD mode — the binary will not be there.

## How the installed backup works

Installs `/usr/local/bin/dhis2-backup` and a daily root cron job (`0 3 * * *`). Behavior:

- Reads settings from `/usr/local/etc/dhis/dhis2-env` (`BACKUP_DIR=/var/pgbackups`)
- Dumps each DHIS2 database **excluding analytics tables** (they are regenerated by DHIS2)
- Dumps the `audit` table separately, then truncates it
- Output: `/var/pgbackups/db-backup/` and `/var/pgbackups/audit-backup/` (dated `YYYYMMDD-HHMMSS-{daily,weekly,monthly}` dirs)
- Optional encryption of dumps
- Optional S3 upload when `s3_access_key`, `s3_secret_key`, and `s3_cluster_id` are all defined

(Re)install or update the script:

```bash
ansible-playbook dhis2.yml --tags backup-script
```

## Manual backup now

LXD — run on the hypervisor host (where you run `deploy.sh`):

```bash
sudo /usr/local/bin/dhis2-backup
sudo ls -lh /var/pgbackups/db-backup/   # confirm a fresh dump exists and is non-trivial in size
```

SSH / distributed — run on the database host:

```bash
sudo /usr/local/bin/dhis2-backup
ls -lh /var/pgbackups/db-backup/
```

Take one before every upgrade, restore, or instance deletion.

## Restore

Follow `docs/how-to/db-backup-and-restore.md`. Dumps are typically `dhis.sql.gz` under dated dirs in `/var/pgbackups/db-backup/`.

**The helper has a different name and different behavior per connection mode** — check which one you are on before quoting a command:

| Mode | Binary | Missing target DB |
| --- | --- | --- |
| LXD | `/usr/local/bin/dhis2-restoredb` on the **hypervisor** | **Aborts.** `dropdb <name>` runs under `set -e` with no `--if-exists` |
| SSH | `/usr/local/bin/dhis2-restore` on the database host (installed from `files/ssh/dhis2-restoredb`, renamed) | Tolerated — logs and continues; only a failing `createdb` aborts |

```bash
sudo /usr/local/bin/dhis2-restoredb /var/pgbackups/db-backup/<dated>/dhis.sql.gz dhis   # LXD
sudo /usr/local/bin/dhis2-restore   /var/pgbackups/db-backup/<dated>/dhis.sql.gz dhis   # SSH
```

**Scratch / new database names on LXD:** because the drop is not guarded, the target must already exist. Create the role and database first — note the owner flag belongs to `createdb`, not `createuser`:

```bash
sudo lxc exec postgres -- sudo -u postgres createuser <db>
sudo lxc exec postgres -- sudo -u postgres createdb -O <db> <db>
sudo /usr/local/bin/dhis2-restoredb /var/pgbackups/db-backup/<dated>/dhis.sql.gz <db>
```

Or load the dump by hand, skipping ownership statements:

```bash
zcat /var/pgbackups/db-backup/<dated>/dhis.sql.gz | grep -v 'ALTER .* OWNER' \
  | sudo lxc exec postgres -- sudo -u postgres psql <db>
```

In-place restore into the live instance DB is destructive. Checklist:

```
Restore progress:
- [ ] 1. Confirm target database name and instance with the human
- [ ] 2. Fresh backup of the current database taken
- [ ] 3. Stop the DHIS2 instance (Tomcat) using the database
- [ ] 4. Run dhis2-restoredb (or the manual LXD steps above)
- [ ] 5. Start Tomcat; verify login and data in the app
- [ ] 6. Record which dump file was restored and when
```

Prefer restoring into a scratch database first when time allows.

## Verify backups are healthy

- Recent files in `/var/pgbackups/db-backup/` with plausible sizes (compare with previous dumps)
- Cron entry present for `dhis2-backup`
- If S3 is configured: object exists in the bucket for the latest cycle
- Disk space on the backup volume — dumps grow with data; analytics exclusion keeps them smaller but not small
